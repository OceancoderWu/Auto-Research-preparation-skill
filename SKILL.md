# Prepare a paper-derived AutoResearch task

Create a task that lets an Agent improve a method under a fixed, executable evaluation protocol. The paper defines the scientific problem and benchmark; the task package defines a bounded search surface and reliable feedback. Deliver working files when the user asks for preparation, not only a proposed prompt.

## Completion boundary: prepare, then hand off

Finish the prerequisites so the user only needs to start AutoResearch with the delivered command. Preparation includes implementation, data/environment setup, real Baseline/Reference runs, checkpoint reload when applicable, public scoring, trusted reward integration, and bounded startup validation on the intended topology within the user's authorization and resources. It does **not** include launching the actual research Agent, long method-search trajectories, or selecting its future best method. A tutorial describing those later phases does not expand this skill's execution scope.

Prepare launch configuration, initial Agent prompt, independent output locations and evidence recording/collection for the later run. Do not automatically execute the launch command. A bounded Harbor smoke may use a fixed known candidate or supported non-search adapter; it must not silently start an optimizing Agent or count as a research trajectory. If the target cannot be verified without starting the actual search, report that specific limitation. Never claim “only start remains” while setup, credentials, assets, validation or an applicable gate is unresolved. User-imposed static-only limits produce a partial preparation report, not a launch-ready claim.

Always deliver the owner-facing report described in [preparation report and handoff](references/preparation-report.md). It is private to the user and may explain the paper and Reference; keep it out of the Agent view.

## Source and scope

1. Read the user's current task card, format rules, constraints, and authorization. If no task card exists, derive a proposed scope from the paper and user request; do not invent an official card. When this program's tutorial or QA skill directory is supplied, read the current versions and record which clauses are active, historical, or example-only. The 2026-09-29 *PCA 双镜像对齐版* and 2026-09-30 QA v0.3.1 align on separate Agent/Verifier images, public Dev feedback and private Hidden grading; use [dual-image Harbor handoff](references/dual-image-harbor.md) when that revision governs. Inspect any supplied example's actual files and call path, not just its README. See the [QA crosswalk](references/qa-crosswalk.md) and [Example lessons](references/example-lessons.md) when those materials apply. Read the paper's method, benchmark, tables, appendix, and evaluation details; inspect the exact released repository revision, configs, data, and license. Retrieve missing primary sources when possible. Do not infer benchmark settings from the abstract or a leaderboard alone.
2. Select one coherent benchmark slice that can be scored programmatically and iterated within the available budget. If the paper has several plausible benchmarks, choose with an explicit rationale; ask only when the user's intended scientific target cannot be inferred. Identify the exact input, output, data split, metric direction, baseline, author method, and resource cost.
3. Make a **protocol alignment record** before coding: for every consequential setting, record the paper claim, released-code/data behavior, task choice, source location, and whether the task is identical, adapted, or unknown. Resolve conflicts explicitly. Keep the original benchmark's reported metrics visible even if the AutoResearch task adds a scalar score. See [benchmark design](references/benchmark-design.md).

## Build the research task

4. Define a meaningful method search surface: model, representation, objective, update rule, inference, or another actual algorithmic component. Check that the candidate parser, guard, and executed interface really accept those changes. A task limited to choosing a few fixed hyperparameter values is insufficient when the current rubric requires method optimization. Freeze data, evaluation, budget, and validity rules fairly. The Agent may discover any legal method, including one similar to the Reference; do not require it to reproduce the Reference.
5. Provide the requested Starter or Scaffold and a reasonable executable formal Baseline; a runnable Starter may also be the Baseline. If the Agent receives only a scaffold, provide a separate runnable expert Baseline and map the score anchor to it. Keep an executable Reference expert-only. Audit actual training amount, correct labels/loss/checkpoint, comparable data and resources, and method provenance before calling the Baseline fair. The Reference demonstrates achievable improvement and remaining headroom; it is not the Agent's answer. Published source may inform it, but copying a repository is not evidence that it matches this task's protocol.
6. Define public iteration feedback and final evaluation before observing candidate results. State what each metric measures, how checkpoints are chosen, seed count, aggregation, normalization anchors, quality gates, invalid outcomes, and stop/budget rules. Follow the current rubric and user's seed decision. If one seed conflicts with an active multi-run or sigma gate, disclose the unmet gate and seek a task-owner exception; one seed cannot establish variance. Never tune the test split, seed, anchor, or Baseline after seeing Reference results to create a favorable score.
7. Write Agent-facing `instruction.md` from the implemented contract, then check every claim against code and configuration. Specify the goal, data and visibility, raw benchmark metrics versus task score, editable files and callable interface, fixed constraints, public command and returned feedback, submission artifact, invalid cases, and completion condition. Give the Agent enough information to research independently without leaking Reference or final test answers. See [instruction design](references/instruction-design.md).

## Make it runnable and verify readiness

8. Implement the actual task package: pinned environment, assets and manifests, Starter, Agent-editable runtime solution, public runner, trusted final evaluator, scorer, packaging, and evidence locations required by the active rubric. Under the active dual-image format, build the Agent from `environment/` and the separate Verifier from `tests/`; keep Public/Dev evaluation in the Agent environment, private final grading in the Verifier, and transfer only the declared final candidate artifacts. Distinguish the Agent task, Baseline/Reference comparison evidence, and later expert Agent trajectories; never generate placeholder scores or trajectories as completed evidence. Align semantic contract (`instruction.md`), machine contract, guards, and executed call path. Keep protected assets outside the Agent's editable surface. An Agent's shell freedom is distinct from its submitted code's edit scope; do not impose command restrictions merely because only one file is graded.
9. Map execution topology explicitly: where the Agent, container, code, data, GPU, public runner, and final verifier live; how commands and metrics return; what credentials each side sees. For Harbor, inspect the installed version and current task tutorial/schema. Do not copy an example's `task.toml`, Docker context, GPU allocation, or reward path without checking the target platform. A remote GPU reached by SSH is a valid topology when actually wired and verified. See [package and readiness](references/package-and-readiness.md).
10. Verify in increasing cost order: source/data hashes and interface checks; both clean image builds and static contract; public command and result parsing; Baseline/Reference runs and checkpoint reload when in scope; and, when authorized and supported, a bounded fixed-candidate Harbor run through Agent exit, declared artifact transfer, separate Verifier execution, and trusted reward. A same-version NOP Trial is a useful optional harness check, but its score or completion cannot replace valid-candidate scoring. Never start the actual research search as a readiness check. For this program, independently review G01–G03, B01–B08, applicable QA01–QA21, and Harbor H01–H06 against actual files. Mark later trajectory/selected-method requirements as post-launch, not passed and not preparation failures; the provided read-only QA skill can assist only after checking its versioned path assumptions against the active tutorial. Its static pass is not a platform run. A request for a launch-ready task includes necessary runtime checks unless the user limits them. Preserve raw logs and failed attempts. Do not fabricate runs, scores, model files, anchors, or a passing status. If the user explicitly prohibits experiments, stop at static verification and mark runtime gates pending.

## Delivery

Write `AutoResearch前置准备报告.md` in an owner-only delivery location, following [the report contract](references/preparation-report.md). Report **design defined**, **statically ready**, **scoring verified**, and **ready for user launch** separately, each with actual evidence. Report **research not started** and **platform final acceptance pending** separately from preparation. Do not generate future trajectories, a selected `best_method/`, or a completed expert-run summary.

Deliver the implemented task, real preparation evidence, private source/protocol alignment, and a concrete launch handoff. Give the exact working directory, commands, configuration, output paths, expected first feedback, stop/resume procedure and evidence collection. If prerequisites are missing, label any proposed command unverified and list the blocker; do not call preparation complete. If the paper lacks usable data/code or an affordable benchmark, state the missing prerequisite and offer an honest adapted design rather than inventing results.

Use the active task specification for directory names, evidence thresholds, seed counts, run durations, and platform commands. The old example and any previous paper's choices are precedents, not universal constants.

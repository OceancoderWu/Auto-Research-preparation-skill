# Owner-facing preparation report and launch handoff

Read when preparing the task and again before delivery. Always create `AutoResearch前置准备报告.md` in an owner-only location, normally beside the submission package, excluded from Docker contexts, Agent mounts and public artifacts. Use Chinese unless the user requests another language. This is a required deliverable, not merely a final chat summary or a proposed outline. Update it to match the final implementation and measured results.

## Audience and evidence

Assume the owner has not read the paper and does not know AutoResearch vocabulary or the package. Explain the scientific problem with a concrete input/output example, introduce each acronym on first use, and explain why each design choice matters before showing code/configuration details. Keep essential explanation in the report; file links provide verification rather than replacing the explanation. Distinguish paper-reported results, local measured results, estimates, and unverified claims throughout. Never imply a local adaptation reproduces the paper's result.

The report may describe Reference methods, paper identity and private design rationale because it is not Agent-facing. Do not include credentials, private keys or raw sensitive labels. Explain relevant private assets by role and approved location. Do not expose the report to the research Agent.

## Required content

Use the following sections, adapting their length to the task. Fill actual facts; do not leave template prose or unsupported “passed” statements.

1. **先看这一页：准备了什么、现在能否启动。** Give the paper/task name, the problem in plain language, what the Agent will improve, and the concrete output it will produce. State design/static/scoring/launch status with evidence, the most important measured B/R result, limitations, and whether any prerequisite remains. Explicitly state that research has not started and platform final acceptance has not occurred. If ready, give the one command or exact small set of commands the user needs; otherwise lead with the blocker, not a ready claim.
2. **论文讲了什么。** Explain motivation, inputs/outputs, core idea and mechanism, experiments and author-reported results, assumptions and limitations. Cite paper sections/tables/appendix and repository revision. Explain which part becomes this task and why the rest is excluded. Separate the paper's claims from what this preparation actually verified.
3. **题目怎样设计。** Explain the selected benchmark slice, a concrete example, the Agent's goal, Starter/Scaffold, legal method search surface, fixed boundaries and resources. Explain why this is method research rather than numeric tuning. Describe what counts as a valid submission and why the task should have research headroom. Record important alternatives and the rationale for the chosen scope without claiming untested alternatives work.
4. **评分 benchmark 怎样设计。** Explain dataset origin, access/license, preprocessing, sample counts, split unit and boundaries, leakage checks, published-test status, and immutable versions/hashes. Walk through Public/Dev feedback and final evaluation separately. Explain raw metrics, direction, units, aggregation, quality gates, B/U normalization with a worked numerical example using measured anchors (or clearly labeled illustrative values while blocked), and invalid/error semantics. State seeds/replicates, independence, paired protocol, stopping/additional-run rule, sigma calculation and deterministic/single-seed exceptions. Identify who owns final assets and why final results cannot be used for selection.
5. **Baseline 与 Reference 怎样设计。** Explain Starter, formal Baseline, score anchor and private Reference as distinct roles, using a side-by-side comparison of algorithms, losses/updates, data, initialization, actual training/execution, selection and resource budgets. Give source/version and adaptation rationale, fairness evidence and limitations. Explain Reference's contribution and why it is neither the unique answer nor U. Show all formal paired runs and recomputed aggregates, normalized reward, sigma separation/headroom and quality gates; link raw logs and reload evidence. Non-training tasks explain their real execution and artifacts rather than inventing checkpoints.
6. **与原论文有哪些一致、冲突和改动。** Embed or summarize the protocol alignment table: setting, paper source/value, code/data source/value, task value, identical/adapted/unknown, rationale and consequence. Cover every consequential difference and explain what comparisons remain justified. List user-approved exceptions and unmet requirements explicitly; do not label an exception ordinary compliance.
7. **实际交付了哪些文件。** Give a compact directory map with each entry's purpose, reader/writer and current status. Link instruction, environment, public runner, trusted grader, launch configuration, Baseline/Reference, real optimization evidence and private report. Explain future expert evidence separately. The owner should know which files they need, which the Agent sees, and which must stay private. Do not imply pending trajectories or best_method already exist.
8. **怎么运行，以及如何隔离。** Show the actual local/container/remote-GPU topology, source transfer, job execution, result return, final artifact synchronization, trusted evaluator identity and permissions. Under the active dual-image tutorial, map the Agent and Verifier build contexts and image IDs, public `public_eval/` path, runtime `/workspace/solution`, `artifacts` transfer, separate `/tests/test.sh` and reward. Explain how candidate code is restricted inside the private Verifier as well as how Reference/final assets and the owner report are excluded from the Agent view. State installed Harbor version/profile, dependencies, authentication readiness without secrets, resource and network controls. For portable delivery, explain how the target can reproduce setup without the author's private machine paths or internal accounts; disclose any approved remote dependency.
9. **已经验证了什么。** Use a compact table: check, result (passed/failed/pending/not applicable/post-launch), actual command or evidence, limitation. Include contract/syntax, data and file integrity, both clean image builds when applicable, Public/Dev feedback, formal B/R comparison, reload when applicable, candidate handoff manifest, separate trusted reward, candidate-private access probes, resource/stability checks and one bounded non-search Harbor Trial. Reconcile the Trial's config, two image IDs, transferred artifact, result, reward and logs. State whether any final-path check used authorized validation data or official Hidden. Distinguish static checks, observed runs and someone else's historical record. For this program include G01–G03, B01–B08, applicable QA/H coverage and explicit post-launch items. No static result proves runtime success.
10. **你接下来怎么启动、观察和停止。** Give executable commands with the actual working directory and configuration, selected Agent model/reasoning from the active specification, independent outputs, how to see the first job/score, log/metric/checkpoint paths, expected time to first feedback and how to distinguish failure from normal waiting. Give stop, resume and artifact collection instructions supported by the installed tools. State measured timing separately from estimated search cost/duration; never promise a final gain. Do not execute the research launch.
11. **限制、未决事项和启动后的验收。** State residual scientific/engineering limitations, missing access or evidence, and exactly what prevents launch if anything. Separate missing prerequisites from expected future outcomes: long research trajectories, Public/Dev best-method selection/revalidation and platform final acceptance happen later. Explain the applicable future evidence contract without presenting it as completed preparation evidence.

Add a short glossary only for terms actually used. Use a diagram or table when it clarifies the pipeline or comparison; a plot is optional and must use real data. Link evidence using paths appropriate to the delivery location; never print secret values.

## Launch handoff requirements

Prepare actual launch configuration or a launcher where helpful, plus the initial Agent prompt and the collection mechanism expected by the active program. Use the installed Harbor/provider interface, not guessed CLI flags. Keep launch files free of embedded secrets and Reference/owner-report exposure. A launch script must not mix unfinished package setup or calibration into the research start merely to hide incomplete preparation. Validate parsing, paths, model availability/authentication and resource configuration without starting method search.

Arrange later recording so running the task can produce the required truthful trajectories and summary inputs. Verify the recorder/exporter with clearly identified test fixtures kept separate from formal evidence; never ship fixtures as actual runs. For tutorial-driven dual runs, prepare independent outputs and the required isolation. If a chosen runtime cannot capture the required fields, implement the collection interface or report a blocker now.

Preparation is complete only when applicable prerequisites have evidence and the launch handoff is executable. Missing credentials, unavailable assets, incomplete B/R evidence, a failed reward path or unsupported launch integration are blockers, not tasks silently passed to the user under “just launch.” Respect explicit limits on experiments/spend; under such limits deliver a useful partial report with pending gates. The report itself is still required even when preparation is blocked.

In the final chat response, link this report, the package and the launch entry, state readiness and any blocker, and confirm that actual AutoResearch has not been started. Do not replace the report with a brief chat reply.

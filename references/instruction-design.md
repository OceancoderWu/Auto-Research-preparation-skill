# Write `instruction.md` as the Agent's executable contract

Use this when drafting or reviewing the Agent-facing prompt. Write it from the *implemented* runner and grader contract, then cross-check every rule against code. Under the supplied teaching tutorial, use the following eight headings exactly and fill them with task-specific facts; another active specification may permit equivalent headings.

1. **Goal:** State the benchmark problem, input, output, primary raw metric and direction in a few sentences. Define a valid submission. Do not prescribe the Reference technique.
2. **Task Setting:** Give input/output schema, class order or tensor shapes, training and public dev data, final evaluation boundary, Starter/Baseline, hardware access route, and relevant distribution shift. If final data are already published, describe them honestly rather than calling them newly secret.
3. **Objective and Metrics:** Give raw metric, metric direction, per-group and per-seed aggregation order, checkpoint selection, quality gates, normalized reward formula and measured anchor provenance. Distinguish public iteration feedback from formal benchmark score; name diagnostics and invalid score/error behavior.
4. **Allowed Scope:** List exact editable files/directories, callable signatures, output shape/schema, permitted algorithm changes, readable assets, public command, and any permitted tool/remote-shell use. Ensure the guard and call path really support that space.
5. **Hard Boundaries:** List frozen data, trainer, metric and verifier; dependency, model/parameter, resource, time, concurrency and artifact limits; network/tool policy; forbidden test access or self-reported scores. Every hard boundary needs an actual guard, trusted check or platform control.
6. **Submission Instructions:** Name the real final files and directory contents, required and optional schema fields if any, and how the trusted evaluator consumes them. Do not invent a JSON submission when the task submits code; do not let candidate stdout or claimed metrics determine reward.
7. **Workflow & Iteration:** Give copyable smoke and Public/Dev commands, where logs and machine-readable feedback appear, the cycle of modify→evaluate→retain/revert, and one-iteration budget. For remote execution, explain source transfer, result return and final artifact synchronization. When this tutorial governs, keep long expert-Agent trajectory duration outside the task-facing prompt; it is distinct from per-iteration limits.
8. **Completion Criteria:** Name interface validity, quality gates, finite trusted score, artifact integrity and protected-file/data conditions. The Agent keeps its best valid candidate, selected using the predeclared Public/Dev rule, until the declared search budget or platform stop; final-test results never select or revise that candidate. A research goal of improving over Baseline does not mean it must reproduce or beat Reference unless the active task contract explicitly says so.

Keep the prompt about the Agent's task. The owner-facing preparation report is a separate private artifact: its paper identity, Reference explanation and undisclosed research directions must not be copied into this prompt or Agent image. Under the supplied QA rubric, omit paper title, arXiv ID and solution repository identity as answer clues unless the task owner explicitly permits disclosure. Put private Reference, final labels, credentials, and expert evidence outside Agent-visible files and image layers. A visible Baseline score is fine when the protocol allows it, but never reveal a private test answer or Reference code by accident.

Useful final cross-check: for each normative sentence in `instruction.md`, point to the implementing line in the runner, guard, scorer, platform config, or immutable data manifest. For each enforced rule, find its explanation in `instruction.md`. Resolve mismatches in both places before declaring readiness.
